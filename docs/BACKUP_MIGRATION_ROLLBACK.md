# 正式切换、备份与回滚

## 当前状态

目前只完成影子数据库和隔离验收。旧 API `8788`、旧页面 `3001` 与真实 `data/state.json` 均保持运行/原状。未获得用户下一次明确确认前，不执行本页的切换步骤。

## 切换前检查

1. 记录 `data/state.json` SHA-256、大小和最后写入时间。
2. 记录 3001/8788 的 PID 与命令行。
3. 对影子库运行 `PRAGMA quick_check` 并记录表计数。
4. 确认真实 Telegram/Webhook 自动化测试发送数为 0。
5. 暂停新增 UI 操作并等待进行中的 Operation 完成。

## 获得确认后的切换顺序

1. 创建带时间戳的独立备份目录。
2. 复制 `state.json`、现有 `.env`、启动脚本和已有数据库（若有）；逐文件记录 SHA-256。
3. 停止旧 3001/8788，确认端口释放。
4. 从真实 `state.json` 的副本创建全新 SQLite；运行 quick_check、人员/绑定/历史成交/Outbox 零补发检查。
5. 使用正式数据目录启动新 API，再启动页面。
6. 验收六视图、对象数量、Target 数、SSE、状态、无历史通知后才宣告完成。

## 回滚触发条件

- SQLite quick_check 非 `ok`。
- 人员、绑定或历史成交数量与迁移报告不一致。
- 旧历史生成 pending notification intent。
- 页面/API readiness 无法恢复，或持续出现未知 Schema 错误。

## 回滚

1. 停止新服务。
2. 保留失败数据库和日志用于诊断，不覆盖备份。
3. 恢复原 `.env` 与原启动方式；`state.json` 使用备份副本校验后恢复。
4. 启动旧 8788/3001 并确认健康。
